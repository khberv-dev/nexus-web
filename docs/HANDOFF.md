# Передача проекта — Nexus Pro

> Разработчик: ИП Ланиес М.Д. | Дата передачи: май 2026

Настоящий документ описывает состав поставки, требования к инфраструктуре и порядок первичного развертывания платформы Nexus Pro.

---

## 1. Что передается

| Компонент | Описание |
|-----------|---------|
| Исходный код | Монорепозиторий: Next.js-приложение (frontend + API), billing-сервис (`services/tbank` на Go) |
| Схема базы данных | Prisma-схема (`prisma/schema.prisma`) + все миграции в `prisma/migrations/` |
| Docker-конфигурация | `Dockerfile`, `docker-compose.yml`, `nginx.conf` |
| CI/CD | Конфигурация GitLab CI (`.gitlab-ci.yml`) — lint, тесты, сборка образа, шаблоны деплоя |
| Документация | `README.md` — архитектура и бизнес-процессы; `ROADMAP.md` — план развития; `HANDOFF.md` — настоящий документ |

Исходный код передается через GitLab-репозиторий. Доступ к репозиторию оформляется отдельно.

## 2. Требования к серверу

### Минимальная конфигурация (production)

| Параметр | Требование |
|----------|-----------|
| CPU | 2 vCPU |
| RAM | 4 GB |
| Диск | 40 GB SSD (без учета хранилища файлов проектов — для этого используется S3) |
| ОС | Ubuntu 22.04 LTS или аналогичный дистрибутив |
| Docker | 24.0+ |
| Docker Compose | 2.20+ |

### Открытые порты

| Порт | Назначение |
|------|-----------|
| 80 | HTTP (редирект на HTTPS) |
| 443 | HTTPS (основное приложение) |
| 22 | SSH (для деплоя через GitLab CI) |

Порты БД (5432), Redis (6379) и billing-сервиса (8090) должны быть закрыты снаружи — они доступны только между контейнерами внутри Docker-сети.

## 3. Быстрый старт

Пошаговый чек-лист развертывания с нуля.

### Шаг 1. Клонировать репозиторий

```bash
git clone https://gitlab.com/<org>/nexus-crm.git
cd nexus-crm
```

### Шаг 2. Создать файл переменных окружения

```bash
cp .env.example .env
```

Заполнить все переменные согласно разделу 4 настоящего документа. Без заполненного `.env` приложение не запустится.

### Шаг 3. Запустить контейнеры

```bash
docker compose up -d
```

После запуска поднимутся: приложение Next.js, PostgreSQL, Redis, billing-сервис, Nginx.

### Шаг 4. Применить миграции базы данных

```bash
docker compose exec app npm run db:deploy
```

Команда применяет все накопленные миграции Prisma к базе данных. Выполняется один раз при первом запуске и после каждого обновления, содержащего изменения схемы.

### Шаг 5. Создать первого администратора

Платформа использует email magic link — OIDC-провайдер не подключён.

1. Подключиться к БД и создать пользователя вручную:
   ```sql
   INSERT INTO "User" (id, email, role, "createdAt", "updatedAt", "sessionVersion")
   VALUES (gen_random_uuid(), 'admin@example.com', 'ADMIN', now(), now(), 1);
   ```
2. Открыть `/login`, ввести email администратора — придёт magic link.
3. Перейти по ссылке и убедиться, что кабинет администратора доступен.

### Шаг 6. Проверить работу

Открыть `https://<домен>/` — должна загрузиться главная страница. Войти под учетной записью администратора и убедиться, что кабинет доступен.

## 4. Переменные окружения

Все переменные задаются в файле `.env` в корне проекта.

### База данных

| Переменная | Описание | Пример |
|-----------|---------|--------|
| `DATABASE_URL` | PostgreSQL connection string | `postgresql://user:pass@db:5432/nexus` |

### Аутентификация

| Переменная | Описание | Пример |
|-----------|---------|--------|
| `NEXTAUTH_URL` | Публичный URL приложения | `https://nexuspro.ru` |
| `NEXTAUTH_SECRET` | Секрет для подписи сессий NextAuth (минимум 32 символа) | `<случайная строка>` |

### Файловое хранилище (S3)

| Переменная | Описание | Пример |
|-----------|---------|--------|
| `S3_ENDPOINT` | Эндпоинт S3 (внутренний, для API-вызовов) | `https://s3.cloud.ru` |
| `S3_PUBLIC_ENDPOINT` | Публичный эндпоинт S3 (для presigned URL, которые видит браузер) | `https://s3.cloud.ru` |
| `S3_REGION` | Регион бакета | `ru-central-1` |
| `S3_ACCESS_KEY` | Access key S3 | `AKIAIOSFODNN7EXAMPLE` |
| `S3_SECRET_KEY` | Secret key S3 | `wJalrXUtnFEMI/K7MDENG/...` |
| `S3_BUCKET` | Имя бакета | `nexus-files` |

### Платежи (T-Bank)

| Переменная | Описание | Пример |
|-----------|---------|--------|
| `BILLING_SVC_URL` | URL billing-сервиса внутри Docker-сети | `http://billing-svc:8090` |
| `TBANK_WEBHOOK_SECRET` | Секрет для проверки подписи webhook от T-Bank | `<из личного кабинета T-Bank>` |

Дополнительные ключи T-Bank (Terminal ID, пароль терминала) настраиваются в конфигурации billing-сервиса (`services/tbank`) — см. его собственный `.env`.

### Email

| Переменная | Описание | Пример |
|-----------|---------|--------|
| `RESEND_API_KEY` | API-ключ Resend | `re_xxxxxxxxxxxx` |
| `EMAIL_FROM` | Адрес отправителя (домен верифицирован в Resend) | `NEXUS <noreply@nexuspro.ru>` |
| `RESEND_SANDBOX` | `1` — слать с `onboarding@resend.dev`, пока домен не верифицирован | `0` |
| `AUTH_EMAIL_DEV_LOG` | `1` — писать ссылку для входа в лог сервера | `0` |
| `SMTP_HOST` | Резервный SMTP: включается наличием хоста (остальное — `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`) | `smtp.example.com` |

### Кэш

| Переменная | Описание | Пример |
|-----------|---------|--------|
| `REDIS_URL` | Redis connection string | `redis://redis:6379` |

### Мониторинг

| Переменная | Описание | Пример |
|-----------|---------|--------|
| `SENTRY_AUTH_TOKEN` | Токен для загрузки source maps при сборке | `sntrys_xxxxxxxxxxxx` |

DSN Sentry (для отправки ошибок в runtime) задается в `next.config.ts` и `sentry.*.config.ts` — при необходимости замены обратитесь к разработчику.

### Служебные флаги

| Переменная | Описание | Пример |
|-----------|---------|--------|
| `SKIP_STAGE_PAYMENTS` | Отключить блокировку этапов на оплату (серверный флаг) | `false` |
| `NEXT_PUBLIC_SKIP_STAGE_PAYMENTS` | То же — для клиентского кода | `false` |
| `DEMO_ACCESS_KEY` | Ключ доступа к демо-режиму (опционально) | `<произвольная строка>` |

В production оба флага `SKIP_STAGE_PAYMENTS` должны быть `false` или не заданы.

## 5. Первый запуск — что настроить сразу после деплоя

### 5.1. Email (magic link) — аутентификация

Платформа использует email magic link через Resend. Zitadel OIDC не подключён.

Убедиться, что заданы:
- `RESEND_API_KEY` — ключ Resend для отправки писем
- `EMAIL_FROM` — адрес отправителя, домен которого верифицирован в Resend
- `NEXTAUTH_URL` — точный публичный URL приложения (без слеша в конце)

Проверка канала после деплоя (под админом):

```bash
curl -s -H "Cookie: <сессия админа>" https://<домен>/api/admin/email/test          # текущая конфигурация
curl -s -X POST -H "Content-Type: application/json" -H "Cookie: <сессия админа>" \
     -d '{"to":"you@example.com"}' https://<домен>/api/admin/email/test            # тестовое письмо
```

Если Resend не настроен или вернул ошибку, письмо уходит резервным SMTP (`SMTP_HOST` и остальные `SMTP_*`).
Когда не настроен ни один канал, отправка пропускается с предупреждением в логе — приложение не падает.

### 5.2. Файловое хранилище

Драйвер выбирается переменной `STORAGE_DRIVER`:

| Значение | Где лежат файлы | Ссылки на скачивание |
|---|---|---|
| `local` | диск контейнера, каталог `/app/uploads` | `/api/storage/get?token=…` (подписанный токен, TTL 15 мин) |
| не задан | S3 (`S3_*` переменные) | presigned URL самого S3 |

**При `STORAGE_DRIVER=local` том `uploads_data` обязателен** — он уже описан в
`docker-compose.yml` для сервиса `app`. Без него файлы живут только внутри контейнера и
исчезают при каждом пересоздании (деплой, рестарт, OOM), а строки `UserFile` в базе
остаются: ссылки начинают отдавать `404 {"error":"Not found"}` при полностью валидном
токене. Восстановить такие файлы нельзя — их придётся загрузить заново.

`STORAGE_URL_SECRET` подписывает ссылки локального драйвера (по умолчанию берётся
`NEXTAUTH_SECRET`). При его смене все ранее выданные ссылки становятся недействительными.
**Пустая строка — это не «значение по умолчанию»**: раньше при `STORAGE_URL_SECRET=""`
ссылки подписывались HMAC с пустым ключом, то есть валидную ссылку на любой файл мог
собрать кто угодно. Теперь пустое значение считается незаданным, а если не задан и
`NEXTAUTH_SECRET` — ссылки не выдаются вовсе.

`STORAGE_LOCAL_ROOT` задаёт каталог загрузок (по умолчанию `uploads/` рядом с приложением).
Держите его вне каталога деплоя (`/var/lib/nexus/uploads`) или на постоянном томе.

Файлы при `local` отдаются по прямому пути `/uploads/<ключ>` — без токена и срока жизни.
Значит, **любой, кто знает или подберёт путь, скачает файл**: ограничения
`StageFile.audience`, договоры и паспорта на этом уровне не защищены, приватность держится
только на случайном uuid внутри ключа. Тот же путь можно снять с приложения и отдать
веб-сервером напрямую:

```nginx
location /uploads/ {
    alias /var/lib/nexus/uploads/;
    add_header Cache-Control "public, max-age=31536000, immutable";
}
```

Если файлы не должны быть публичными, используйте S3-драйвер (presigned-ссылки с TTL).

#### S3

1. Создать бакет с именем, указанным в `S3_BUCKET`.
2. Применить политику CORS из файла `s3-cors.xml` в корне репозитория:
   ```bash
   aws s3api put-bucket-cors --bucket <имя-бакета> --cors-configuration file://s3-cors.xml
   ```
3. Убедиться, что у сервисного аккаунта S3 есть права `GetObject`, `PutObject`, `DeleteObject` на этот бакет.

### 5.3. DNS

Указать A-запись домена на IP-адрес сервера. Настроить SSL-сертификат (рекомендуется Let's Encrypt через Certbot или Nginx Proxy Manager).

### 5.4. T-Bank — платежи

1. Получить Terminal ID и пароль терминала в личном кабинете T-Bank.
2. Зарегистрировать webhook-URL: `https://<домен>/api/billing/webhook`.
3. Указать секрет webhook в `TBANK_WEBHOOK_SECRET`.
4. Убедиться, что billing-сервис (`services/tbank`) настроен с корректными ключами.

### 5.5. Sentry — мониторинг ошибок

DSN проекта задан в коде. Если необходимо подключить собственный Sentry-проект — обратитесь к разработчику для замены DSN в конфигурации.

## 6. Что не включено в MVP

Перечисленные функции находятся в плане развития (Этап 2 и далее) и в текущую поставку не входят.

| Функциональность | Этап | Текущее решение |
|-----------------|------|----------------|
| ЭДО / электронная подпись (СБИС) | 2 | Договоры подписываются офлайн или через внешний сервис |
| Квалификационный тест внутри платформы | 2 | Тест проводится через Zoom, статус обновляется вручную администратором |
| Рейтинги специалистов от клиентов | 2 | Рейтинг выставляется вручную администратором |
| Каталог специалистов с фильтрами | 2 | Выбор специалиста — через администратора |
| Автоматические выплаты (T-Bank Payout) | 2 | Выплаты инициируются вручную через администратора |
| Видео-визитки специалистов | 2 | Поле зарезервировано в БД, загрузка не реализована |
| PDF-генерация итоговых актов | 2 | Акт создается в системе, PDF не формируется |
| Реальные специалисты в карусели лендинга | 2 | Данные захардкожены, карусель не подключена к БД |
| Sharp-сжатие изображений | 2 | Изображения сохраняются без оптимизации |

| Что нужно | Для чего | Статус |

| Webhook-секрет T-Bank | Подтверждение платежей | Требуется |

| S3-бакет (cloud.ru или иной провайдер) | Хранение файлов проектов | Требуется |
| Тексты email-уведомлений | Финальные формулировки писем | Требуется |
| Поля брифа заказчика | Структура анкеты при создании заказа | Требуется (если нужны изменения) |
| Поля анкеты онбординга специалиста | Структура анкеты при регистрации специалиста | Требуется (если нужны изменения) |
