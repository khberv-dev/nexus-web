# Онлайн-платформа для дизайна интерьеров

> Маркетплейс, соединяющий заказчиков с профессиональными дизайнерами интерьеров. Платформа обеспечивает полный цикл работы: от онбординга специалиста до финальной выплаты, с контролем качества на каждом этапе.

## О проекте

Платформа решает две проблемы одновременно: заказчики не знают как найти проверенного дизайнера и не понимают как контролировать качество работы, а специалисты тратят время на поиск клиентов вместо профессиональной работы.

**Модель работы:** заказчик платит предоплату при старте проекта, деньги удерживаются на платформе. Специалист выполняет работу поэтапно, платформа проверяет качество на каждом шаге. Деньги переходят специалисту только после того, как заказчик принял финальный результат.

**Целевой сегмент:** коммерческие объекты — офисы, рестораны, торговые помещения. Там используются повторяющиеся решения и одни и те же поставщики, что делает процесс предсказуемым и масштабируемым.

---

## Целевая аудитория

| Сторона | Кто это | Основная боль |
|---------|---------|---------------|
| Заказчик | Владелец или управляющий коммерческим объектом | Нет доверенного дизайнера, непонятно как контролировать качество |
| Специалист | Дизайнер интерьеров или архитектор | Нестабильный поток клиентов, споры по оплате |
| Администратор | Менеджер проектов платформы | Нужен инструмент для управления всеми проектами и специалистами |

---

## Роли в системе

### Заказчик (CLIENT)
Регистрируется на платформе, заполняет бриф, выбирает специалиста или получает назначение от администратора. Оплачивает проект предоплатой. На каждом этапе просматривает результат и принимает решение — принять или отправить на доработку.

### Специалист (SPECIALIST)
Проходит многоэтапный онбординг перед получением доступа к заказам. Выполняет проект в пять этапов, загружает файлы, получает обратную связь от модератора и заказчика. Получает оплату после подписания акта.

### Администратор (ADMIN)
Сотрудник платформы. Проводит модерацию работ специалиста перед передачей заказчику, управляет онбордингом новых специалистов, назначает специалистов на заказы, контролирует выплаты. Это не технический специалист — это менеджер проектов.

## Архитектура и стек

### Общая схема

Монолитное веб-приложение на **Next.js 16 (App Router)**. Все три роли работают в одном приложении, разделение происходит через **middleware** по JWT-ролям (NextAuth). Аутентификация — **email magic link** через Resend. Файлы хранятся в **S3-совместимом** хранилище (MinIO/AWS S3). Платежи и биллинг вынесены в отдельный сервис `services/tbank`. Чат реализован внутри этапов и заказов. Уведомления доставляются по двум каналам: email (Resend/Nodemailer) и in-app (хранятся в БД, отображаются в интерфейсе).

### Технологии

| Слой | Технология | Назначение |
|------|-----------|------------|
| Frontend + API | Next.js **16.2.0** (App Router) + React **19** | UI, SSR, API (Route Handlers) |
| База данных | PostgreSQL **15** + Prisma **7** | Основное хранилище данных |
| Аутентификация | NextAuth v4 + email magic link (Resend) | Сессии/токены, роли, логин |
| Файловое хранилище | S3 (AWS SDK) + MinIO (локально) | Файлы дизайн-проектов, presigned URL |
| Платежи/биллинг | `services/tbank` (отдельный сервис) | Интеграция с T-Bank, статусы платежей/выплат |
| Кэш/очереди | Redis **7** | Кэширование, вспомогательное хранилище для интеграций |
| Email | Resend + Nodemailer | Транзакционные уведомления |
| Мониторинг | Sentry | Отслеживание ошибок, source maps, алерты |
| Деплой | Docker Compose (Next `output: standalone`) | Контейнеризация, запуск окружения |
| CI/CD | GitLab CI | lint/test/build (+publish docker image), деплой шаги-шаблоны |

### Принцип масштабирования

MVP строится как монолит — это быстро и достаточно для первых реальных заказов. После валидации бизнес-модели модули поэтапно выносятся в микросервисы. Монолит не переписывается — он наращивается.

## Бизнес-процессы

### A. Онбординг специалиста

Прежде чем брать заказы, специалист проходит многошаговый онбординг. Каждый шаг может завершиться одобрением или отказом с указанием слабых мест.

```
Анкета → Квалификационный тест → Интервью → Изучение регламентов → Договор → Активен
```

На MVP тест и интервью проводятся через Zoom, администратор вручную меняет статус в системе. Платформа хранит статусы и отправляет уведомления на каждом переходе.

Если специалист не прошел этап — платформа указывает на слабые места и приглашает вернуться после повышения квалификации.

### B. Создание заказа

1. Заказчик регистрируется и заполняет **бриф** — подробную анкету о проекте (площадь, стиль, бюджет, особые требования).
2. Администратор проверяет бриф и при необходимости уточняет детали.
3. Администратор назначает подходящего специалиста.
4. Платформа формирует договор по заказу, стороны подписывают, администратор подтверждает договор. Только после подтверждения заказ переходит в статус **ACTIVE** и специалист может начинать работы по этапам.
5. Перед стартом каждого этапа заказчик вносит **аванс за этап** (в текущей реализации — минимум для первого этапа). Платеж удерживается на платформе и “размораживается” при приемке этапа.

### C. Выполнение проекта — этапы

Этапы идут последовательно (следующий этап может быть заблокирован до завершения предыдущего). Каждый этап проходит цикл: специалист загружает файлы → администратор проверяет → заказчик принимает решение → администратор фиксирует результат.

#### Этапы проекта (текущая модель)

- Концепция
- Планировка
- Визуализация
- Рабочая документация
- Спецификация на материалы

#### Правила правок

- **Правки заказчика**: до **3 бесплатных раундов** на этап. Далее этап переводится в режим **доп. оплаты**, и без оплаты правок работа по этапу не продолжается.
- **Правки по модерации**: **1 бесплатный круг** на этап. Далее — также через **доп. оплату**.

Примечание: биллинг может быть временно отключен флагом окружения (в таком режиме этапы продолжаются без блокировки на оплате).

### D. Завершение и оплата

1. На каждом этапе при приемке формируется **акт по этапу**.
2. Платеж за этап удерживается при оплате и **выплачивается специалисту при приемке этапа**.
3. Когда **все этапы проекта приняты**, заказ переводится в статус **DONE**, и заказчик получает финальное уведомление.


## Что не входит в MVP

| Функциональность | Когда появится |
|-----------------|----------------|
| ЭДО и электронная подпись (СБИС) | Этап 2 |
| Рейтинги и каталог специалистов | Этап 2 |
| Квалификационный тест внутри платформы | Этап 2 |
| Автоматические выплаты специалистам (T-Bank Payout) | Этап 2 |
| Видео-визитки специалистов | Этап 2 |
| PDF-генерация итоговых актов | Этап 2 |
| Кабинет поставщика / фабрики | Этап 3 |
| Заказ мебели из проекта | Этап 3 |
| Логистика на объект | Этап 3 |
| Мобильное приложение | Этап 3+ |

На текущем этапе **ЭДО/электронные подписи**, **рейтинги** и **PDF-генерация актов** не реализованы. Квалификационный тест и интервью проводятся вручную (через Zoom), администратор вручную переводит статус в системе.

## Зависимости от заказчика

Разработка ряда блоков невозможна без материалов со стороны заказчика. Задержка материалов приостанавливает соответствующий этап разработки.

| Блок | Что нужно от заказчика |
|------|----------------------|
| Онбординг специалиста | Поля анкеты, вопросы теста, чек-листы модерации |
| Заказ и бриф | Поля и структура брифа |
| Стейт-машина | Чек-листы модерации для каждого из этапов проекта |
| Email-уведомления | Тексты всех писем |
| Оплата | Merchant ID и ключи T-Bank |
| Запуск | Домен, сервер, DNS |

## Глоссарий

**MVP** — минимальная рабочая версия, достаточная для проведения первых реальных сделок.

**Бриф** — подробная анкета заказчика: площадь, стиль, бюджет, особые требования к проекту.

**Онбординг** — процесс приема специалиста на платформу: анкета → тест → интервью → регламенты → договор.

**Стейт-машина** — логика переходов проекта между статусами. Определяет кто и когда может совершить следующее действие.

**Модерация** — проверка работы специалиста администратором до передачи заказчику.

**Раунд правок** — один цикл: заказчик написал замечания → специалист исправил → сдал повторно.

**Акт выполненных работ** — документ, подтверждающий приемку работы. После его подписания деньги переходят специалисту.

**А.Д.Р.** — администратор/менеджер платформы. Модерирует работы, ведет специалистов, управляет проектами.

**Magic link** — ссылка для входа, которая отправляется на email. Позволяет войти без пароля.

**Presigned URL** — временная ссылка для прямой загрузки/скачивания файла из S3 без промежуточного сервера.
